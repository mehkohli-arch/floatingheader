Employee Experience Design System

Turning a patchwork of internal apps into one consistent, accessible system that designers and engineers can build on quickly.

First, what is a design system?

Like LEGO for software

A design system is a shared library of reusable building blocks, such as colors, text styles, buttons and forms, plus clear rules for using them.

Every team builds with the same pieces, so products look and work the same, they're accessible to everyone, and nobody has to reinvent the wheel.

The situation

Many apps, no shared rules

CMG Financial builds many internal apps for its employees. Engineers build them with PrimeNG, a ready-made library of code components.

Over time, each app started using those components differently. Styling was improvised and accessibility gaps crept in. Without one standard, designers and engineers lost time to rework and unclear instructions, and employees got an inconsistent experience.

The answer was a central design system, matched directly to the code engineers already use, that served both designers and developers.

My part: I was the company's go-to design systems expert. I guided and mentored the lead designer, and when they moved to another project, I took over and finished the work.

The problem

Inconsistency was slowing everyone down

  • The same component was used differently from app to app.
  • Engineers needed repeated clarification at every handoff.
  • Design files were so bloated they slowed designers down.
  • New designers needed 5+ days to get up to speed.

The challenge: how might we build a design system that matches the engineers' code, speeds up everyone's work, improves accessibility and keeps every team consistent?

How I approached it

Six steps from chaos to system

  1. Audit what exists

    I reviewed every component across the internal apps and logged inconsistencies, duplicates and accessibility issues. I also asked developers about the technical limits they work within.

  1. Set the rules

    I defined clear rules for text, spacing and color.

    I used atomic design: start with the smallest basics (colors, spacing, type), combine them into elements (buttons, inputs), then into full patterns (forms, tables). Like letters forming words, then sentences.

  1. Make it work for everyone

    I made sure components meet WCAG accessibility standards: readable color contrast, visible focus outlines, labels for screen readers, and full keyboard use. I tested the core flows with a keyboard and a screen reader.

  1. Write it down

    I co-wrote guidelines explaining why and when to use each component, with accessibility notes and specs engineers can build from directly.

  1. Coach and collaborate

    I gave ongoing feedback through design critiques, and co-ran design and engineering meetings to make sure the system was buildable and adopted.

  1. Finish the job

    I took ownership of the unfinished work: the design tokens and the complete component builds.

    Design tokens are named settings, like "primary color" or "small spacing," defined once and used everywhere. Change a token, and every product using it updates. I finalized a token setup that keeps the whole system consistent and easy to extend.

Challenges

What made it hard

Working within the code library

PrimeNG is a strong base but strict. Some designs didn't map one-to-one, so I documented clearly for developers.

Different habits

Designers were each using components slightly differently. Fixing that took buy-in and onboarding, not just technical fixes.

Writing for two audiences

Designers needed usage and accessibility guidance. Developers needed exact technical mapping. It took constant iteration to serve both.

Fast files, still flexible

Removing too many variations limits designers; keeping too many slows files down. I had to balance both.

Changing habits

Moving designers from custom builds to the shared system needed hands-on support, training and trust.

Guiding without taking over

Supporting the lead designer's ownership, then picking up the gaps once they moved on.

What I learned

Systems are about people

This project showed me the impact of mentorship, and the importance of stepping in when a project's momentum is at risk. As the expert and later the owner, I was able to:

  • Support another designer's growth and ownership.
  • Build accessibility and scale into the system from the start.
  • Deliver complete, token-based components that teams actually adopt.
  • Show system thinking, cross-team alignment and adaptability.
