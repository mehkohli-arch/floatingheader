Why this matters

Design systems now have a second reader

For years, a design system had one audience: the people who design and build products. Now it has a second one. AI tools read the system too, and they build with it.

That changes what a design system is for. My goal isn't only to make today's screens consistent. It's to give CMG the scaffolding to grow: new products, new platforms, new themes and new ways of working, including ones we haven't thought of yet. A system built that way works just as well for a new designer, an employee prototyping an idea, or an AI tool.

Four shifts are changing how design systems work. For each one, here's what the research says, and how I put it into practice at CMG on two systems: Clear 2.0, our employee loan software, and our new customer-facing design system.

  • Design tokens: named settings, like "page background" or "small spacing," defined once and used everywhere.
  • Storybook: a living library of the real coded components that designers and other employees use to build their own tools and prototypes.
  • PrimeNG: the ready-made code library our engineers build with.
  • MCP: a standard way for AI tools to plug into other software and read its information.
Shift 1 of 4

AI can read the system

A design system used to be something people browsed. Now it's something AI tools read before they build.

Design system experts saw this coming early. In 2024, Brad Frost wrote that an AI trained on a design system's code and documentation becomes "a component boilerplate generator on steroids."1 The tools have caught up. Storybook now connects directly to AI agents, giving them the real components, examples, documentation and tests so they build "production grade UI instead of hallucinating their way through it."2 Figma's MCP server pulls a team's variables and components straight into AI coding tools, and can generate "design system rules aligned to your codebase."3

The design system is becoming the source AI tools check before they build anything. So it has to be built for them from the start.

Shift 2 of 4

Token names now have to carry meaning

Design tokens and theming aren't new.4 Teams have used them for years to manage brands and light and dark modes. What's changing is who reads them.

A designer can look at a token called "pink-600" and know it's the brand color on buttons. An AI tool can't. It only gets the name. Tools like Figma's MCP server now pass a team's variables straight into AI coding tools,3 so the name is the instruction. "pink-600" tells an AI what a color looks like. "primary-action" tells it what the color is for, and where to use it.

Shift 3 of 4

Written rules matter as much as components

AI tools follow instructions, so the rules have to be written down.

Anthropic recommends giving Claude a project file with "coding conventions, and team norms," and scoping more specific rules to the parts of a project they apply to.5 Vercel describes its component registry as "a distribution specification designed to pass context from your design system to AI models," so its AI tool can generate prototypes that match a team's design system "without manual overrides."6

Prose is part of the system now. Explaining why and when to use a component is what keeps an AI from guessing.

Shift 4 of 4

Everyone can build, so the system has to hold the line

AI is already everywhere in design system work. In zeroheight's 2026 survey of design system practitioners, 82% of teams use AI in some form.7

But the same research shows the risk. 59% report UI being built that bypasses their design system, and 50% say other teams' AI use is creating real problems. Teams are happiest using AI for documentation, and least happy with AI-generated designs. Only 17% rate their documentation "very AI-ready."7

AI multiplies whatever system it's given. A clear system multiplies consistency. A vague one multiplies mistakes.

Project 1 · Clear 2.0, our employee loan software

Dark mode in under a month

Clear 2.0 is the software CMG employees use every day to manage loans. The team wanted dark mode, but technical debt stood in the way: one-off pieces of code built outside the design system, each styled its own way.

Instead of patching screens one by one, I fixed the foundation.

  1. Add a semantic layer to the tokens

    I restructured our tokens and added a layer named by purpose, like "primary action" or "page background," instead of by color. Switching to dark mode now means changing what each purpose points to, not redesigning every screen.

  1. Follow PrimeNG more closely

    I aligned the token structure with PrimeNG, the code library engineers use, so design and code speak the same language.

  1. Work around the one-offs

    I planned around the older one-off code so dark mode could ship without waiting for a full rewrite.

  1. Put every component in Storybook

    I built a Storybook version of every component, in both React and Angular, so designers and other employees can build their own tools and prototypes with the same parts that ship.

What I learned

Clarity scales, for people and AI

  • Fix the foundation first. A semantic token layer turned dark mode from a redesign into a switch.
  • Write for two readers. Rules clear enough for a new designer are clear enough for an AI tool.
  • Meet people where they are. Matching PrimeNG and engineers' frameworks makes the system easy to adopt, and Storybook makes it easy for everyone else to build with.
  • Build for the platform you'll have, not just the one you have. Good scaffolding makes the next product, theme or tool cheaper to add.
