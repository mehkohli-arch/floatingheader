AI-Ready Design Systems

AI tools now read and build with design systems, the same way designers and engineers do. This case study covers what that changes, and how I set up CMG's systems to support it as the company grows.

Why this matters

AI tools use design systems too

Design systems were written for the designers and engineers who build products. AI tools now read them as well, and use them to build screens and prototypes.

My goal is for CMG's design systems to keep working as the company adds new products, platforms, themes and ways of working. A system set up that way is just as usable for a new designer, an employee prototyping an idea, or an AI tool.

Below are four changes in how design systems are being used. Each one covers what the research says and how I applied it at CMG, on two systems: Clear 2.0, our employee loan software, and our new customer-facing design system.

  • Design tokens: named settings, like "page background" or "small spacing," defined once and used everywhere.
  • Storybook: a living library of the real coded components that designers and other employees use to build their own tools and prototypes.
  • PrimeNG: the ready-made code library our engineers build with.
  • MCP: a standard way for AI tools to plug into other software and read its information.
Shift 1 of 4

Figma and Storybook now connect to AI

Storybook and Figma now give AI tools direct access to a team's components and documentation.

In 2024, Brad Frost wrote that an AI trained on a design system's code and documentation becomes "a component boilerplate generator on steroids."1 Since then, Storybook has added a direct connection for AI agents, giving them the real components, examples, documentation and tests so they build "production grade UI instead of hallucinating their way through it."2 Figma's MCP server pulls a team's variables and components straight into AI coding tools, and can generate "design system rules aligned to your codebase."3

That means a design system now needs to be organized and documented in a way AI tools can use.

Shift 2 of 4

Token names need to describe their purpose

Teams have used design tokens for years to manage brands and light and dark modes.4 Now that AI tools read them too, the names carry more weight.

A designer who sees a token called "pink-600" knows from experience that it's the brand color used on buttons. An AI tool only has the name to go on. Figma's MCP server passes a team's variables directly into AI coding tools,3 and a name like "primary-action" tells the tool what the color is for and where to use it, which "pink-600" doesn't.

Shift 3 of 4

AI tools need written rules

AI tools can only follow guidance that's written down.

Anthropic recommends giving Claude a project file with "coding conventions, and team norms," and scoping more specific rules to the parts of a project they apply to.5 Vercel describes its component registry as "a distribution specification designed to pass context from your design system to AI models," so its AI tool can generate prototypes that match a team's design system "without manual overrides."6

Written guidance on when and why to use each component has become part of the system itself, because it's what an AI tool relies on in place of experience.

Shift 4 of 4

More people are building, so consistency is harder

Most design system teams already use AI. In zeroheight's 2026 survey of design system practitioners, 82% of teams use AI in some form.7

The same survey points to a downside: 59% report UI being built that bypasses their design system, and 50% say other teams' AI use is creating real problems. Teams are happiest using AI for documentation, and least happy with AI-generated designs. Only 17% rate their documentation "very AI-ready."7

Project 1 · Clear 2.0, our employee loan software

Dark mode in under a month

Clear 2.0 is the software CMG employees use every day to manage loans. The team wanted dark mode, but technical debt stood in the way: one-off pieces of code built outside the design system, each styled its own way.

I handled it at the token level, so screens didn't have to be patched one at a time.

  1. Add a semantic layer to the tokens

    I restructured our tokens and added a layer named by purpose, like "primary action" or "page background," instead of by color. Switching to dark mode now means changing what each purpose points to, not redesigning every screen.

  1. Follow PrimeNG more closely

    I aligned the token structure with PrimeNG, the code library engineers use, so design and code speak the same language.

  1. Work around the one-offs

    I planned around the older one-off code so dark mode could ship without waiting for a full rewrite.

  1. Put every component in Storybook

    I built a Storybook version of every component, in both React and Angular, so designers and other employees can build their own tools and prototypes with the same parts that ship.

Takeaways

What I learned

  • Start with the tokens. Adding a semantic layer meant dark mode didn't require redesigning screens.
  • Write guidelines for people and AI. If a new designer can follow them, an AI tool usually can too.
  • Match the tools people already use. Following PrimeNG and the engineers' frameworks made the system easy to adopt, and Storybook made it easy for everyone else to build with.
  • Plan for growth. A system that's easy to extend makes the next product, theme or tool cheaper to add.
